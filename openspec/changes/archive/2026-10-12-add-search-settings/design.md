## Context

動機・対象capabilityは `proposal.md` を参照。現在は `Application.swift` の `ApplicationController` がNSPanelとメニュー、Carbonの単独F1登録を管理し、`SheetStore` が `folderBookmark` の復元・選択・インデックスを管理する。SwiftUI AppのSettings Sceneを使う構成ではなく、NSApplicationを直接起動する。設定画面、ホットキーの保存、登録失敗のUIは存在しない。

フォルダの現行変更処理は先に既存インデックスを消してからbookmarkを作成するため、新しい設定UIでは検証・永続化の準備を先行させる必要がある。設定・UI・登録状態をまたぐ変更と互換性の扱いがあるためdesignを作成する。

## Goals / Non-Goals

**Goals:** 適用済み設定、編集中の値、実際のキー登録状態を区別し、設定UI・メニュー・パネルが同じ状態を参照する。フォルダ設定とショートカットは項目ごとに適用し、一方の失敗が他方を変更しない。

**Non-Goals:** SwiftUI Appライフサイクルへの移行、大規模なファイル分割、OS全体のキー競合の事前検出、App Sandboxへの移行。検索関数・Markdown変換・画像アクセス規則の変更は行わない。

## Decisions

### 1. AppKitの設定ウィンドウにSwiftUIフォームを載せる

`ApplicationController` が通常のNSWindowを一つ保持し、NSHostingViewの設定フォームを表示する。メニューから再度開いた場合は同じウィンドウを前面に出す。検索パネルとは別のウィンドウなのでフォルダパスやキー編集中のフォーカスを分離できる。フォームには現在のフォルダ、パス入力、選択ボタン、フォルダの適用、ショートカット記録欄、その適用、エラーを配置する。未適用値は画面を閉じる際に破棄する。

代替のSwiftUI Settings Sceneは起動構造の変更を必要とするため採用しない。設定を検索パネル内に埋める方式は呼び出し・検索の操作を複雑にするため採用しない。

### 2. キーコードと修飾キーを保存し、表示文字列を分離する

設定モデルはキーコードとCommand/Option/Control/Shiftの正規化済み修飾フラグを保持し、UserDefaultsの専用キーへ保存する。未保存なら `kVK_F1` と `cmdKey` を既定値にする。現行版にはキー保存値がないためF1からの値移行は不要。保存値の形式・キー範囲が壊れている場合は設定画面へ通知し、既定値を候補とする。登録が失敗したらキー未登録の状態を保持する。

自由入力の文字列表現を解析する方式より、設定画面で実際のキーを記録する方式のほうが記号・修飾キーの曖昧さが少ない。記録中だけAppKitのキーイベントを受け、修飾だけを除外し、修飾なしはF1〜F20に限定する。既に登録中のキーも記録できるよう、記録開始時に現キーの登録を一時解除し、記録終了・キャンセル・ウィンドウ終了時に復元する。復元失敗もUIに通知する。記録は保存・適用ではない。

キー表示はキーコードと現在のキーボード配列から作成し、Carbon用フラグへの変換と分ける。Fnは保存する修飾キーに含めず、ハードウェア設定による追加操作として説明する。別ライブラリの導入は避け、現在のCarbon登録機構を拡張する。

### 3. 新しい登録の成功後に旧キーを解除する

イベントハンドラは一度だけ設置し、ホットキー登録と分ける。キー変更では新しい組み合わせを別のEventHotKeyIDで登録し、成功後に旧登録を解除して適用済みモデル・UserDefaultsを更新する。同じキーへの適用は登録済みなら再登録せず成功扱いとし、未登録なら再試行する。登録失敗なら旧登録を保持し、エラーをフォームへ返す。イベントは現在有効なIDのみ処理する。

旧登録を先に解除してから新登録する方式は、失敗時の復旧にも再登録失敗の可能性があるため採用しない。起動時の登録失敗は設定済み値と登録可否を区別し、メニュー・パネルの案内には利用不可を示す。メニューによる検索・設定表示はキー登録から独立させる。

### 4. フォルダの検証・bookmark生成後に対象を切り替える

入力パスは空白を整え、`~` を展開し、絶対パスへ正規化する。個別ファイル、存在しないパス、読み取り不能なフォルダを拒否する。既存の `folderBookmark` を唯一の復元元として維持し、パス文字列の別保存による不一致を作らない。NSOpenPanelの選択結果も同じ適用経路に渡す。

新フォルダへのアクセス、ディレクトリ列挙、bookmark生成を準備し、失敗時は新規アクセスを解放して既存状態を維持する。成功時のみ保存、旧アクセス解放、フォルダ変更、キャッシュ破棄、強制スキャンを行う。準備時に読めても後で削除・権限変更が起きる競合はスキャン時のエラーとして知らせる。各Markdownの読み込み失敗は既存の失敗件数表示に従う。

フォルダ変更時だけ再構築する。設定画面を開く、同一フォルダを再適用する、キーのみを変更する操作はスキャンしない。既存メニューとパネルのフォルダ選択も同じ経路へ揃え、設定画面が開いていれば適用済みパスを同期する。

### 5. プレースホルダーとキー案内のみを検索UIへ反映する

TextFieldのプレースホルダーを `name.title` にし、queryの初期値と再表示時リセットは空文字のままとする。`title` は文書の `#` タイトルではなく検索構文の `##` 見出しを指す。`rank` の実装・優先順位・空検索の候補列挙は変更しない。メニューとパネルのキー案内は同じ適用済みキー表示・登録状態を参照する。

キー呼び出しは既存の表示切替だけを実行し、UserDefaults読込・パス検証・スキャンを呼び出し経路に入れない。起動時・60分ごと・手動の更新タイミングを維持する。NSPanelのSpace設定とMarkdownプレビューは維持し、新しいフォルダでは各エントリの元ファイルURLを基準に既存の相対画像解決を行う。50ms未満は従来の性能目標であり保証値ではない。

## Risks / Trade-offs

- [Carbon登録の成功だけでは全OSキー競合を検出できない] → 登録エラーと実際の呼び出しを別に検証し、メニューから設定変更できる入口を確保する。
- [記録中のキー登録解除・復元とウィンドウの閉じ方で状態がずれる] → 記録終了・キャンセル・閉じるすべての経路で復元し、実機で既定キーと現在キーの再記録を確認する。
- [キーボード配列とFn動作により表示キーと物理操作が異なる] → キーコードと表示を分離し、US/JIS、Fn設定を実機確認する。
- [フォルダ検証後にアクセス条件が変わる] → 適用前失敗と適用後スキャン失敗を区別し、ユーザーが対象を修正できるエラーを表示する。
- [設定の保存・ウィンドウ追加で表示が遅くなる] → 設定処理を呼び出し経路から分離し、既定・変更キー双方でフォーカスとスキャン未実行を確認する。

## Migration Plan

1. 既存bookmarkを変更せず読み込み、ショートカット未保存時だけCmd+F1を選ぶ。
2. 設定モデル・登録・UIを導入し、READMEへ新しい既定値、設定操作、Fnの制約を記載する。OpenSpecガイド/configの古いソースパス・固定F1の記述も実装に合わせる。
3. 構造検証、ビルド、失敗分岐の検証、macOS操作確認を実施し、未確認項目はそのまま記録する。
4. ロールバック時は旧版が新しいショートカット保存値を無視して単独F1を登録する。bookmarkのキー・形式を維持するため対象フォルダは継続利用できる。基本仕様の同期・アーカイブは別の明示的なworkflowで行う。
